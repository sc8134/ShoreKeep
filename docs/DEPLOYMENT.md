# Deploying Shorekeep

This guide covers the production path: Postgres, migrations, a public demo, and signed desktop releases.

## What runs where

| Piece | Command | Notes |
|---|---|---|
| API + UI | `uvicorn backend.api.main:app` | Serves the single-page UI and `/v1/*` |
| Worker | `python -m backend.engine.worker` | Claims queued jobs, runs yt-dlp/MY-DL/ffmpeg |
| Migrations | `alembic -c alembic.ini upgrade head` | Creates or upgrades the Postgres schema |
| Combined | `bash start.sh` | API + worker in one container, for single-service hosts |

`start.sh` lives in `services/backend` and is copied into the Docker image. Use it on Render or Fly where only one process can own the volume.

The Docker image is `infra/Dockerfile.backend`. It expects the repo root as the build context.

## Database

Local development and the desktop app keep using SQLite with no setup. Production uses Postgres:

```
DATABASE_URL=postgresql://user:password@host:5432/shorekeep
```

`postgres://` URLs from managed providers are accepted and converted to the psycopg 3 driver automatically.

Schema management:

```bash
# from the repo root
alembic -c services/backend/alembic.ini upgrade head
```

In Docker the same command runs against `/app/alembic.ini`.

`DB_AUTO_CREATE=true` creates tables with SQLModel instead of Alembic. Use it only for throwaway demo databases. Normal deployments keep it `false` and run migrations.

The API refuses to start against a database that is missing tables and tells you to run Alembic.

Concurrency guarantees with Postgres:

- quota check plus insert runs under `pg_advisory_xact_lock`, so two API processes cannot both pass the same hourly limit;
- the worker claims jobs with `SELECT ... FOR UPDATE SKIP LOCKED`, so several workers never take the same job.

## Option A: Render blueprint

The repo includes [render.yaml](../render.yaml). It creates:

- a Postgres database (`shorekeep-db`);
- one web service running the API and the worker together;
- a 10 GB disk mounted at `/data` for media and work files;
- a pre-deploy migration step.

Steps:

1. Push the repo to GitHub.
2. In Render, choose **New > Blueprint** and select the repo.
3. When prompted, set `PUBLIC_BASE_URL` to the final URL, for example `https://shorekeep.onrender.com`.
4. Deploy. The health check is `/v1/health`.

`SECRET_KEY` is generated by Render. Keep it stable: changing it invalidates stored BYOC cookies and IP hashes.

To run the full product instead of the public demo, change `DEMO_MODE` to `"false"` and configure Paddle billing.

## Option B: Fly.io

The repo includes [fly.toml](../fly.toml).

```bash
fly launch --copy-config --no-deploy
fly volumes create shorekeep_data --size 10 --region sin
fly secrets set \
  DATABASE_URL="postgresql://user:password@host:5432/shorekeep" \
  SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(48))')" \
  PUBLIC_BASE_URL="https://<your-app>.fly.dev"
fly deploy
```

The release command runs `alembic upgrade head` before the new version starts. The app stays on one machine so the API and worker share the same volume.

For more than one machine, set `STORAGE_BACKEND=r2` with an R2 bucket and move the worker to its own process group. Local storage assumes one shared `/data` folder.

## Option C: Docker Compose on a VPS

```bash
cp .env.example .env
# edit .env: SECRET_KEY, POSTGRES_PASSWORD, PUBLIC_BASE_URL, COOKIE_SECURE=true
docker compose -f infra/docker-compose.prod.yml up -d --build
```

This stack runs Postgres, a one-shot `migrate` service, the API, and a separate worker. Both app containers share `media_data`.

## Demo mode

Set `DEMO_MODE=true` to run a public demo that cannot be abused as a free downloader:

| Effect | Value |
|---|---|
| Max preset for every visitor | `DEMO_MAX_PRESET` (default `480p`) |
| Max file size | `DEMO_MAX_FILESIZE_MB` (default `200`) |
| Jobs per hour | `DEMO_JOBS_PER_HOUR` (default `5`) |
| Concurrent jobs | `DEMO_MAX_ACTIVE_JOBS` (default `1`) |
| Billing | disabled, Upgrade and Billing buttons hidden |
| Cookies | rejected with a clear message |
| UI | banner explains the demo caps |

The caps apply to guests, free accounts, and Pro accounts alike. They are enforced server-side in `plans.py`, not just hidden in the UI.

Recommended demo settings:

```
DEMO_MODE=true
DEMO_MAX_PRESET=480p
DEMO_MAX_FILESIZE_MB=200
TURNSTILE_ENABLED=true
TURNSTILE_SITE_KEY=...
TURNSTILE_SECRET=...
```

## Storage

- `STORAGE_BACKEND=local` (default): files live in `DATA_DIR/media`. Requires a shared disk between API and worker.
- `STORAGE_BACKEND=r2`: finished files upload to Cloudflare R2 and downloads redirect to short-lived presigned URLs. Use this for multi-machine or serverless hosts.

## Desktop release signing

### Windows

Signing is wired into `infra/windows/build.ps1`. It signs the app executable, then rebuilds the installers so they contain a signed binary, then signs the installers. It also writes `dist/installer/SHA256SUMS.txt`.

Provide one of these before running the build:

| Variable | Meaning |
|---|---|
| `SHOREKEEP_SIGN_CERT_PATH` | Path to a `.pfx` file |
| `SHOREKEEP_SIGN_CERT_PASSWORD` | Password for that `.pfx` |
| `SHOREKEEP_SIGN_THUMBPRINT` | SHA1 thumbprint of a certificate already in the Windows store |
| `SHOREKEEP_SIGN_SUBJECT` | Subject name of a store certificate |
| `SHOREKEEP_TIMESTAMP_URL` | Timestamp server, default `http://timestamp.digicert.com` |
| `SIGNTOOL` | Optional explicit path to `signtool.exe` |

Buy a standard code signing certificate (OV is enough to remove "Unknown publisher"; EV helps reputation faster). Export it as `.pfx`, then:

```powershell
$env:SHOREKEEP_SIGN_CERT_PATH = "C:\keys\shorekeep.pfx"
$env:SHOREKEEP_SIGN_CERT_PASSWORD = "..."
powershell -ExecutionPolicy Bypass -File infra/windows/build.ps1
```

Without a certificate the build still succeeds and prints that artifacts are unsigned.

### GitHub release workflow

`.github/workflows/release.yml` runs on tags like `v0.4.2`:

1. runs the test suite;
2. builds Windows on `windows-latest`, with Inno Setup installed;
3. builds Linux and macOS bundles (best effort, they do not block the release);
4. combines checksums;
5. publishes a GitHub release with the artifacts.

Secrets for Windows signing:

| Secret | Value |
|---|---|
| `WINDOWS_CERT_PFX_BASE64` | Base64 of your `.pfx` file |
| `WINDOWS_CERT_PASSWORD` | Its password |

Create the base64 value with:

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\keys\shorekeep.pfx")) | Set-Clipboard
```

Without these secrets the workflow still releases unsigned installers, suitable for testing only.

### macOS

`infra/macos/build.sh` uses `SIGN_IDENTITY` for `codesign` and `NOTARY_PROFILE` for `notarytool`. Create the notary profile once:

```bash
xcrun notarytool store-credentials "shorekeep-notary" \
  --apple-id "you@example.com" --team-id "TEAMID" --password "app-specific-password"
```

Then:

```bash
SIGN_IDENTITY="Developer ID Application: Your Name (TEAMID)" \
NOTARY_PROFILE="shorekeep-notary" \
bash infra/macos/build.sh
```

The script produces `dist/Shorekeep-macos-<version>.zip` and a `.sha256` file.

### Linux

```bash
bash infra/linux/build.sh
```

Produces `dist/Shorekeep-linux-<arch>-<version>.tar.gz` and a `.sha256` file. No signing is required. The tray uses the Xorg backend, and the native window needs GTK WebKit if `pywebview` can find it; otherwise the app falls back to the default browser.

## Verifying downloads

```bash
sha256sum -c SHA256SUMS.txt          # Linux
shasum -a 256 -c Shorekeep-*.sha256  # macOS
Get-FileHash .\Shorekeep-Setup-0.4.2.exe -Algorithm SHA256   # Windows
```

Windows users can also right-click the installer, choose Properties, and check the Digital Signatures tab.

## Production checklist

- `SECRET_KEY` is a long random value and stays stable.
- `COOKIE_SECURE=true` behind HTTPS.
- Postgres is reachable from the API and worker; migrations run on deploy.
- `PUBLIC_BASE_URL` matches the real site, including scheme.
- Turnstile is enabled on public deployments.
- Billing is configured (Paddle keys and price ids) or intentionally disabled.
- Storage backend matches the host topology (local disk shared, or R2).
- Installers are signed and checksums published.
- Backup policy exists for Postgres and for R2 or the media disk.
